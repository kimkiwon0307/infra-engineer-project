### Logrotate 설정

Nginx의 `access.log`, `error.log`가 계속 누적되어 디스크 공간을 과도하게 사용하는 것을 방지하기 위해 Logrotate 정책을 확인하고 수정했습니다.

#### 1. Logrotate 설정 확인

```bash
cat /etc/logrotate.d/nginx
```

#### 2. Logrotate 설정 수정

```bash
sudo nano /etc/logrotate.d/nginx
```

```text
/var/log/nginx/*.log {

    daily
    # 로그를 매일 회전

    missingok
    # 대상 로그 파일이 없어도 오류를 발생시키지 않음

    rotate 30
    # 회전된 로그를 최대 30개 보관

    compress
    # 오래된 로그 압축

    delaycompress
    # 가장 최근에 회전된 로그는 다음 회전 시 압축

    dateext
    # 회전된 로그 파일명에 날짜 추가

    dateformat -%Y%m%d
    # 날짜 형식을 YYYYMMDD 형태로 지정

    notifempty
    # 로그 파일이 비어 있으면 회전하지 않음

    create 0640 www-data adm
    # 새 로그 파일을 0640 권한으로 생성
    # 소유자 www-data / 그룹 adm

    sharedscripts

    prerotate
        if [ -d /etc/logrotate.d/httpd-prerotate ]; then \
            run-parts /etc/logrotate.d/httpd-prerotate; \
        fi \
    endscript

    postrotate
        invoke-rc.d nginx rotate >/dev/null 2>&1
    endscript
}
```

#### 3. 날짜 형식 적용

```text
dateext
dateformat -%Y%m%d
```

회전된 로그를 다음과 같이 날짜 기반으로 관리할 수 있도록 설정했습니다.

```text
access.log
access.log-20261014
access.log-20261013.gz

error.log
error.log-20261014
```

> **Logrotate 설정 목적**
>
> - 로그 파일의 무제한 증가 방지
> - 디스크 사용량 관리
> - 일정 기간 로그 보관
> - 오래된 로그 압축
> - 날짜별 로그 관리

### Reverse Proxy 설정

Client가 WAS 서버의 Spring Boot 애플리케이션에 직접 접근하지 않고 WEB 서버의 Nginx를 통해 접근하도록 Reverse Proxy를 구성했습니다.

#### 설정 목적

1. WEB 서버를 외부 요청의 단일 진입점으로 사용
2. WAS 서버의 8080 포트를 외부에 직접 노출하지 않음
3. 향후 HTTPS, Load Balancing, 접근 제어 등의 기능을 WEB 계층에서 처리할 수 있도록 구성

#### Nginx 설정

```nginx
location / {
    proxy_pass http://192.168.111.142:8080;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

#### 주요 설정

- `proxy_pass` : 요청을 WAS 서버 `192.168.111.142:8080`으로 전달
- `Host` : Client가 요청한 Host 정보를 WAS에 전달
- `X-Real-IP` : 실제 Client IP 정보를 WAS에 전달
- `X-Forwarded-For` : Proxy를 거친 Client IP 정보를 전달
- `X-Forwarded-Proto` : Client가 사용한 HTTP/HTTPS 프로토콜 정보를 전달

#### 설정 적용

```bash
sudo nginx -t
sudo systemctl reload nginx
```

#### 동작 확인

```bash
curl -i http://localhost/health
curl -i http://localhost/health/db
```

정상 응답:

```text
/health     → 200 OK
/health/db  → 200 OK
```

#### 요청 흐름

```text
Client
   ↓ HTTP :80
WEB01 - Nginx
   ↓ HTTP :8080
WAS01 - Spring Boot
```

### 장애 테스트

1. **장애 상황** : Nginx 서비스 중지
2. **증상** : 웹 페이지 접속 불가
3. **확인 순서**
   - `systemctl status nginx`
   - `ps -ef | grep nginx`
   - `sudo ss -tnlp | grep :80`
   - 웹 브라우저 또는 `curl` 접속 테스트
   - `/var/log/nginx/error.log` 확인
4. **원인** : Nginx 서비스 중지
5. **조치**

```bash
sudo systemctl start nginx
```

6. **검증**
   - 서비스 상태 확인
   - 80번 포트 LISTEN 확인
   - `curl` 정상 응답 확인
   - 웹 접속 확인

7. **배운 점**

> WEB 장애 발생 시  
> **서비스 → 프로세스 → 포트 → HTTP → 로그**  
> 순서로 확인하여 장애 범위를 단계적으로 좁힐 수 있습니다.

### 애플리케이션 전용 계정 생성

Spring Boot 애플리케이션을 `root` 계정으로 실행하지 않고 별도의 서비스 계정인 `infraapp`으로 실행하도록 구성했습니다.

#### 1. 시스템 계정 생성

```bash
sudo useradd \
  --system \
  --home /opt/infra-app \
  --shell /usr/sbin/nologin \
  infraapp
```

#### 2. 계정 확인

```bash
id infraapp
```

주요 옵션:

- `--system` : 일반 사용자가 아닌 서비스용 시스템 계정 생성
- `--home /opt/infra-app` : 애플리케이션 디렉터리를 Home 경로로 지정
- `--shell /usr/sbin/nologin` : 해당 계정으로 직접 로그인하지 못하도록 제한

> **설정 목적**  
> 애플리케이션에 취약점이나 장애가 발생하더라도 시스템 전체의 `root` 권한까지 영향을 받지 않도록 최소 권한 원칙을 적용했습니다.

### systemd 서비스 등록

Spring Boot 애플리케이션을 수동으로 실행하지 않고 Linux 서비스로 관리하기 위해 systemd에 등록했습니다.

#### 1. 서비스 파일 생성

```bash
sudo nano /etc/systemd/system/infra-app.service
```

```ini
[Unit]
Description=Infra Spring Boot Application
After=network.target

[Service]
User=infraapp
Group=infraapp

WorkingDirectory=/opt/infra-app

EnvironmentFile=/etc/infra-app/infra-app.env

ExecStart=/usr/bin/java -jar /opt/infra-app/app.jar

Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

#### 주요 설정

- `User=infraapp` : 애플리케이션을 전용 계정으로 실행
- `Group=infraapp` : 실행 그룹 지정
- `WorkingDirectory` : 애플리케이션 작업 디렉터리 지정
- `EnvironmentFile` : DB 접속 정보 등의 환경변수 파일 지정
- `ExecStart` : Spring Boot JAR 실행 명령
- `Restart=on-failure` : 비정상 종료 시 자동 재시작
- `RestartSec=5` : 장애 발생 후 5초 뒤 재시작
- `WantedBy=multi-user.target` : 일반적인 서버 부팅 과정에서 서비스가 시작될 수 있도록 설정

### 트러블슈팅

#### Spring Boot 실행 시 8080 포트 충돌

Spring Boot 애플리케이션을 실행하는 과정에서 8080 포트가 이미 사용 중이어서 애플리케이션이 정상적으로 실행되지 않는 문제가 발생했습니다.

**증상**

Spring Boot 실행 시 8080 포트를 사용할 수 없다는 오류가 발생했습니다.

**확인**

```bash
sudo ss -tnlp | grep :8080
```

8080 포트를 사용하는 프로세스를 확인한 결과 기존에 설치되어 있던 Tomcat 서비스가 실행 중인 것을 확인했습니다.

```bash
sudo systemctl status tomcat10
```

**원인**

기존 외장 Tomcat이 8080 포트를 사용하고 있었으며 Spring Boot의 Embedded Tomcat도 동일한 8080 포트를 사용하려고 하여 충돌이 발생했습니다.

**조치**

기존 Tomcat 서비스를 중지했습니다.

```bash
sudo systemctl stop tomcat10
sudo systemctl disable tomcat10
```

이후 Spring Boot 서비스를 다시 시작했습니다.

```bash
sudo systemctl restart infra-app
```

**검증**

```bash
sudo systemctl status infra-app
sudo ss -tnlp | grep :8080
curl -i http://localhost:8080/health
```

Spring Boot 애플리케이션이 정상적으로 8080 포트를 사용하고 `/health` 요청에 `200 OK`를 반환하는 것을 확인했습니다.

**배운 점**

> 애플리케이션이 특정 포트를 사용할 수 없을 경우 단순히 프로세스를 강제 종료하기보다 해당 프로세스가 systemd 서비스로 관리되고 있는지 확인해야 합니다.  
> systemd에서 자동으로 관리되는 서비스의 경우 프로세스만 종료하면 다시 실행될 수 있으므로 서비스 단위로 중지 및 비활성화해야 합니다.

### MySQL Bind Address 설정

기본 설정에서는 MySQL이 로컬 인터페이스에서만 요청을 받을 수 있기 때문에 WAS 서버의 원격 접속을 허용하기 위해 Listen 주소를 확인했습니다.

#### 설정 파일

```bash
sudo nano /etc/mysql/mysql.conf.d/mysqld.cnf
```

기본 설정:

```text
bind-address = 127.0.0.1
```

DB 서버의 IP로 변경:

```text
bind-address = 192.168.111.143
```

또는 모든 IPv4 인터페이스에서 Listen해야 하는 경우:

```text
bind-address = 0.0.0.0
```

설정 변경 후:

```bash
sudo systemctl restart mysql
```

확인:

```bash
sudo ss -tnlp | grep :3306
```

> **주의**  
> `bind-address`는 접속을 허용할 Client IP를 지정하는 옵션이 아닙니다.  
> MySQL이 **DB 서버의 어떤 네트워크 인터페이스에서 요청을 받을지** 지정하는 옵션입니다.
>
> WAS 서버의 접속 가능 여부는 MySQL 계정의 Host 설정과 방화벽 정책을 함께 사용하여 제어합니다.

### DB 수동 백업

MySQL 데이터 손실 상황에 대비하여 `mysqldump`를 이용한 논리 백업을 구성했습니다.

#### 백업 디렉터리 생성

```bash
sudo mkdir -p /backup/mysql
sudo chown root:root /backup/mysql
sudo chmod 700 /backup/mysql
sudo ls -ld /backup/mysql
```

`700` 권한을 사용하는 이유:

```text
owner  → 읽기 / 쓰기 / 실행
group  → 권한 없음
other  → 권한 없음
```

> DB 백업 파일에는 실제 서비스 데이터가 포함되어 있으므로 일반 사용자가 접근하지 못하도록 권한을 제한했습니다.

---

### MySQL 백업 실행

```bash
sudo sh -c 'mysqldump marble > /backup/mysql/marble_$(date +%Y%m%d_%H%M%S).sql'
```

백업 파일 확인:

```bash
sudo ls -lh /backup/mysql
```

생성 예:

```text
marble_20261012_181530.sql
```

> `sudo sh -c`를 사용한 이유는 `>` 리다이렉션이 현재 Shell에서 처리되기 때문입니다.  
> `sudo mysqldump ... > /backup/mysql/file.sql` 형태로 실행하면 리다이렉션에는 `sudo` 권한이 적용되지 않아 Permission denied가 발생할 수 있습니다.

### DB 자동 백업 스크립트

수동 백업 작업을 자동화하기 위해 Shell Script를 작성했습니다.

파일:

```text
/usr/local/sbin/mysql-backup.sh
```

스크립트:

```bash
#!/bin/bash

set -e

BACKUP_DIR="/backup/mysql"
DB_NAME="marble"
DATE=$(date +%Y%m%d_%H%M%S)

mysqldump "$DB_NAME" > "$BACKUP_DIR/${DB_NAME}_${DATE}.sql"

find "$BACKUP_DIR" \
    -type f \
    -name "${DB_NAME}_*.sql" \
    -mtime +7 \
    -delete
```

#### 주요 설정

- `#!/bin/bash` : Bash Shell로 스크립트 실행
- `set -e` : 명령 실행 중 오류 발생 시 스크립트 종료
- `BACKUP_DIR` : 백업 저장 경로
- `DB_NAME` : 백업 대상 데이터베이스
- `DATE` : 백업 파일명에 사용할 현재 날짜와 시간
- `mysqldump` : MySQL 논리 백업 실행
- `find ... -mtime +7 -delete` : 일정 기간이 지난 백업 파일 삭제

---

### systemd Timer 자동 백업

DB 백업 스크립트를 매일 자동 실행하기 위해 systemd Service와 Timer를 구성했습니다.

#### 1. Backup Service 생성

```bash
sudo nano /etc/systemd/system/mysql-backup.service
```

```ini
[Unit]
Description=MySQL Backup Service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/mysql-backup.sh
```

`Type=oneshot`은 명령을 한 번 실행한 후 종료되는 작업에 사용합니다.

---

#### 2. Backup Timer 생성

```bash
sudo nano /etc/systemd/system/mysql-backup.timer
```

```ini
[Unit]
Description=Run MySQL Backup Daily

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

#### 주요 설정

- `OnCalendar=*-*-* 02:00:00` : 매일 오전 2시에 실행
- `Persistent=true` : 예약 시간에 서버가 꺼져 있었다면 다음 부팅 후 누락된 작업 실행
- 같은 이름의 `.timer`는 기본적으로 같은 이름의 `.service`를 실행

동작 구조:

```text
mysql-backup.timer
        ↓
mysql-backup.service
        ↓
```

### 트러블슈팅

#### WAS01에서 DB01 MySQL 원격 접속 거절

**증상**

WAS01 서버에서 MySQL 원격 접속을 시도했지만 연결이 거절되었습니다.

```bash
mysql -h 192.168.111.143 -u marble -p
```

오류:

```text
ERROR 2003
Connection refused
```

**확인**

DB01에서 3306 포트 상태를 확인했습니다.

```bash
sudo ss -tnlp | grep :3306
```

결과:

```text
127.0.0.1:3306
```

MySQL이 Loopback 인터페이스에서만 요청을 받고 있음을 확인했습니다.

**원인**

MySQL 설정의 `bind-address`가 다음과 같이 설정되어 있었습니다.

```text
bind-address = 127.0.0.1
```

따라서 DB01 외부의 WAS01 서버에서 접근할 수 없었습니다.

**조치**

설정 파일을 수정했습니다.

```bash
sudo nano /etc/mysql/mysql.conf.d/mysqld.cnf
```

```text
bind-address = 192.168.111.143
```

설정 변경 후 MySQL을 재시작했습니다.

```bash
sudo systemctl restart mysql
```

**검증**

DB01:

```bash
sudo ss -tnlp | grep :3306
```

WAS01:

```bash
nc -zv 192.168.111.143 3306
mysql -h 192.168.111.143 -u marble -p
```

정상적으로 DB 연결이 가능한 것을 확인했습니다.

**배운 점**

> `bind-address`는 접속을 허용할 Client 주소를 지정하는 설정이 아니라 MySQL이 DB 서버의 어떤 네트워크 인터페이스에서 요청을 받을지 지정하는 설정입니다.
>
> DB 접근 제어는 `bind-address`, 방화벽, MySQL 계정의 Host 및 권한을 각각 구분해서 이해해야 합니다.
